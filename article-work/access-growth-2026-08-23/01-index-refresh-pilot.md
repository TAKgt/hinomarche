# 商品鮮度pilotの安全設計

実装日: 2026-08-23 JST

## 目的

公開商品の30日鮮度を回復できるかを、燕三条の調理器具に限定して匿名件数で確認する。検索順位や流入の増加を保証する処理ではなく、technical対象から外れている商品を安全に再確認できるかを測るpilotである。

初回対象は次に固定した。

- カテゴリ: `kitchen`
- 検索語: `燕三条 調理器具`
- API返却・DB更新の上限: 30件

`npm run pilot:index-refresh`を実行し、カテゴリ設定とDBの匿名集計だけを読み取った。

## 安全条件

1. カテゴリ・検索語は初回pilotの固定値以外を拒否する。上限は1〜30件だけを許可する。
2. 外部previewとDB更新では、カテゴリ、検索語、上限を引数で明示する。
3. DB更新では、previewのAPI返却数、既存一致数、更新候補数、入力変更数、technical復帰候補数、結果fingerprint、承認トークンがすべて再取得結果と一致する必要がある。
4. API結果に重複行がある場合、更新候補が0件の場合、または上限を超えた場合は停止する。
5. 更新候補は、取得元の商品識別子が一意に一致し、現在公開中で、同じカテゴリにある既存商品だけとする。新規候補、現在非公開の商品、カテゴリ外の商品は更新しない。
6. 商品追加・削除、カテゴリ変更、`search_rank`、`demand_score`、`featured_score`、shadowランキングを変更しない。
7. 判定入力が変わった商品はAIを呼ばず、従来の安全処理どおり`pending`・非公開へ戻す。古いAI判定とCTAは表示せず、`noindex,follow`を維持する。
8. 30日・180日の品質条件やtechnical index判定は変更しない。
9. 更新直前の対象行を`.backups/index-refresh-pilot/`へ権限600で保存する。更新日時が途中で変わった行は更新・rollbackとも停止する。
10. 標準出力とエラーには商品ID、商品名、URL、認証情報を出さず、匿名件数だけを出す。

## 外部previewの承認パッケージ

まだ実行していない。承認を得た場合だけ次の1回を行う。

- 操作対象: 楽天市場の商品検索、`kitchen`の`燕三条 調理器具`
- 読み取り・書き込み: 楽天APIとDBを読み取り。DB書き込みは0件
- 対象件数と上限: API最大30件、1カテゴリ、1検索語
- API・AI利用量: 楽天API 1回、AI API 0回
- 想定費用: AI費用0円。楽天ウェブサービスの2026年8月24日確認時点の公式利用規約は、別途定める場合に利用料金の支払いが必要とする一方、この公開規約に1リクエストの金額は示していない。追加費用0円とは断定せず、アカウント側の現行条件を確認できるまで実行しない
- DBへの影響: 読み取りのみ。商品・計測・ランキングの変更0件
- バックアップ: 書き込みがないため不要
- 停止条件: 対象設定不一致、承認トークン不一致、API失敗、31件以上、対象外データ、既存キー重複
- rollback: 書き込みがないため不要
- commit・push・deploy・Search Console: すべて0件、実行しない

実行コマンドはREADMEに記載した。承認トークンは既定dry-runが返した対象固定の値を用いる。

## DB更新を承認する前に必要な情報

外部preview後に、匿名の実測値を提示して別途承認を得る。少なくとも、API返却数、既存一致数、現在公開中の一致数、更新候補数、入力変更数、AI再判定候補数、technical復帰候補数、処理時間、fingerprint、更新上限、想定DB書き込み件数を明記する。

更新承認後もAI再判定は実行しない。入力変更があった場合のAI候補は件数だけを示し、現行料金と対象件数を改めて確認して別承認とする。プロジェクト内の旧見積もりは1件約0.3〜0.5円だが、実課金の根拠にはしない。

## rollback

DB更新が承認され実行された場合、更新前値、更新直前・直後の`updated_at`、checksumを持つbackupを作成する。rollbackはそのbackupの専用ディレクトリ内パス、期待件数、backupから算出したrollback承認トークンが一致する場合だけ実行する。pilot実行後に別の更新が入った行は上書きせず停止する。
