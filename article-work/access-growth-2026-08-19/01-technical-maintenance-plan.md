# 商品URLの30日鮮度を維持するdry-run計画

## 結論

公開880商品を現在の観測coverageで30日以内に再確認し続けることはできない。公開商品全体には1日29.33件のユニーク再確認が必要だが、直近30日に確認された公開商品は172件、1日換算5.73件だった。

現在のtechnical対象167件だけなら1日5.57件で理論上は観測値内に収まる。しかし観測能力の97%を使うため、検索上位30件への再出現漏れ、Cronの時間切れ、商品説明変更によるAI再判定を吸収する余裕がほぼない。そこで観測coverageの80%を安全枠にし、まず137件を30日維持集合としてdry-run選定した。これは1日4.57件の再確認で維持できる計算である。

この計画は外部商品API 0回、DB書き込み0件、AI判定0件で作成している。現在の公開状態、30日・180日基準、CTA、sitemapは変更していない。

## 現行処理能力と必要量

| 項目 | 件数・上限 |
|---|---:|
| 日次Cron | 1回 |
| Cron最大実行時間 | 60秒 |
| 1回のカテゴリ | 4 |
| 1カテゴリの検索語 | 1 |
| 楽天検索の最大返却 | 30行 / 検索語 |
| API返却行の理論上限 | 120行 / 日 |
| AI判定枠 | 5件 / 日 |
| 公開880件を30日維持する必要量 | 29.33件 / 日 |
| technical対象167件を維持する必要量 | 5.57件 / 日 |
| 直近30日の公開商品確認coverage | 5.73件 / 日 |
| 80%安全枠の137件を維持する必要量 | 4.57件 / 日 |

120行/日は検索結果の生データ上限であり、120商品の更新成功を意味しない。同じ商品が複数回返ること、既存商品が上位30件に出ないこと、DB処理が60秒内に終わらないことがある。実績に近い値として、直近30日のユニーク公開商品172件を観測proxyに使った。

## 原因

1. 23カテゴリのうち1日4カテゴリ、各1検索語を巡回するため、カテゴリ自体は約6日で一巡するが、商品は検索上位30件へ再出現しないと更新されない。
2. 既知の長尾商品は上位30件から外れると再確認されない。公開880件のうち708件が30日超となっている。
3. 検索結果は既存商品の更新だけでなく新規候補の追加にも使う。全カテゴリは最低公開数12件を満たしているため通常巡回だが、新規探索は継続する。
4. 入力が変わった既存商品は安全のためpendingへ戻る。AI枠は5件/日だが、pending全体は2,738件あり、現在のスキーマでは「以前公開されていたpending」を新規pendingから確実に識別できない。
5. Cronが毎回60秒内に完走しているかは未確認である。返却120行を逐次upsertした後にAI判定を行う現在の構造では、完走可否を実行ログなしに断定できない。

## 137件の選定規則

dry-runは個別商品情報を出力せず、次の順で優先度を付けた。

1. Search Consoleで個別ページ43表示、関連クエリ36表示を確認できた燕三条テーマ
2. 公開・人手確認済みの一次情報台帳が揃う商品
3. 既存重点4テーマ（燕三条、炊飯器、今治、日本茶）
4. DB内の需要スコア、販売先レビュー件数、検索順位、既存featuredスコア
5. 1カテゴリに偏らないカテゴリ巡回

## 実装した安全なローカル変更

- `npm run audit:index-quality` に、公開商品だけの除外理由、カテゴリ別公開数・technical対象・30日超、`product_evidence` の件数と商品単位の編集品質判定を接続した。
- `npm run plan:index-refresh -- --focus-theme=tsubame_kitchen` を追加した。外部API、AI、DB書き込みを行わず、現在値から日次必要件数と維持候補の集計だけを返す。
- plannerの戻り値には商品ID、商品名、URLを含めない。
- 監査・plannerの純粋関数に回帰テストを追加した。

## 今回は実行しない外部・本番操作

### 承認後の最小検証案

1. まず1カテゴリ・1検索語だけで、API返却30行のうち既存維持候補へ一致するユニーク件数、処理時間、入力変更件数を読み取りpreviewする。
2. previewで既存更新率と60秒内の余裕を確認できた場合だけ、「維持候補の既存更新を先に処理し、残り時間で新規探索する」実装を検討する。
3. 入力変更商品は旧AI判定・CTAを復活させず、5件/日のAI枠内で再判定する。新規候補より以前公開された商品を優先するには、履歴を安全に識別する方法が別途必要である。
4. 7日間の小規模実行後、対象カテゴリの30日超減少、technical対象維持、Cron完走率を確認してから拡大する。

### 費用と承認

- 外部商品API実行、DB更新、AI再判定、Vercel環境変数・Cron変更はすべて承認待ち。
- 商品入力が変わらなければAI再判定は不要。変わった場合のプロジェクト内見積もりは1件約0.3〜0.5円で、上限5件/日なら約1.5〜2.5円/日、30日で約45〜75円。ただし実課金は利用サービスの現行料金確認後に判断する。
- 楽天APIの利用料金・上限・現行規約は今回変更しておらず、追加費用なしとは断定しない。

### 期待効果と戻し方

- 期待効果は、重要商品の30日超によるsitemap脱落を減らし、燕三条など表示機会があるページの商品リンクを安定させること。検索順位や流入増を保証しない。
- 今回のplannerは読み取り専用なので、本番状態のロールバックは不要。コードを取り込まなければ影響はない。
- 将来の更新実行は、対象カテゴリ・件数・実行時間を固定し、実行前集計とDBバックアップ手順を用意する。失敗時は新規実行を止め、30日・180日基準を緩めず、noindexとCTA非表示の安全側を維持する。
